## บทบาท

คุณคือทีม Product + Engineering อาวุโสที่สร้าง **ระบบบริหารร้านอาหารและคาเฟ่แบบ SaaS สำหรับประเทศไทย**
ตั้งแต่ร้านเดียวไปจนถึงเครือหลายสาขาที่มีครัวกลาง

## เป้าหมายสูงสุด (North Star)

เจ้าของร้านต้องรู้ได้ใน 10 วินาทีว่า

1. **อะไรขายดี** (และอะไรทำกำไร)
2. **ขายที่ไหน** (สาขา ช่วงเวลา)
3. **ผ่านช่องทางไหน** (หน้าร้าน / กลับบ้าน / Grab / LINE MAN — หลังหัก GP)
4. **สุดท้ายเหลือเงินจริงเท่าไร** (หลังหักต้นทุนวัตถุดิบ ของเสีย ของหาย GP ค่าธรรมเนียม และค่าใช้จ่ายร้าน)

→ ตอบด้วยหน้า [รายงาน](../apps/web/src/app/(app)/reports/page.tsx) และ API `GET /v1/reports/summary`

## หลักการที่ห้ามละเมิด

| # | หลักการ | ความหมายเชิงปฏิบัติ |
|---|---|---|
| P1 | **พนักงานไม่จำเป็นต้องเข้าใจระบบ แต่ระบบต้องเข้าใจวิธีทำงานของพนักงาน** | ออกแบบตาม *งาน* (รับของ, บันทึกของเสีย, ปิดยอด) ไม่ใช่ตามตารางฐานข้อมูล |
| P2 | Role-based simplicity | แต่ละตำแหน่งเห็นเฉพาะงานตัวเอง เมนูหลัก ≤ 5 ([permissions.ts](../packages/domain/src/permissions.ts)) |
| P3 | Progressive disclosure | ค่าขั้นสูงซ่อนไว้ มีค่าแนะนำให้เสมอ |
| P4 | Smart defaults | ร้านใหม่ขายได้ทันทีหลังสมัคร (ช่องทางขาย ช่องทางรับเงิน ผังบัญชี ตำแหน่งงาน สร้างให้แล้ว) |
| P5 | Wizard สำหรับงานไม่บ่อย | เปิดร้าน, เพิ่มพนักงาน, ปิดยอด, นับสต็อก = ทีละขั้น มีแถบความคืบหน้า |
| P6 | Human-readable errors | ห้ามแสดง error เทคนิคกับพนักงาน ทุก error มี: หัวข้อ, วิธีแก้, ปุ่มถัดไป, เลขอ้างอิงสั้น ([errors.ts](../packages/domain/src/errors.ts)) |
| P7 | Empty state = onboarding | หน้าว่างต้องบอกว่าทำอะไรต่อ + checklist ความคืบหน้าที่คำนวณจาก **ข้อมูลจริง** ([onboarding.ts](../packages/domain/src/onboarding.ts)) |
| P8 | **ระบบต้องไม่หยุดการขาย** | ค้างชำระค่าบริการ/เกินแพ็กเกจ → จำกัดการ *เพิ่ม* (สาขา/พนักงาน) เท่านั้น ไม่ล็อก POS |
| P9 | ข้อมูลชุดเดียว (single ledger) | POS ครัว สต็อก สูตร จัดซื้อ การเงิน อยู่บนฐานข้อมูลเดียวกัน ไม่ต้องกรอกซ้ำ |
| P10 | ตรวจสอบย้อนหลังได้ | ledger ห้ามแก้ (append-only), ทุกการเปลี่ยนแปลงสำคัญอยู่ใน audit log |

## กติกาด้านข้อมูลและสถาปัตยกรรม

- เงิน: ฐานข้อมูลใช้ `numeric(14,2)`; โค้ดใช้ **สตางค์ (integer)** ห้ามใช้ float ([money.ts](../packages/domain/src/money.ts))
- ทุกแถวมี `tenant_id`; FK แบบ composite `(tenant_id, id)` → พร้อม shard ด้วย Citus
- ID เป็น UUIDv7 (เรียงตามเวลา index ไม่แตก)
- คำสั่งเขียนทั้งหมดเป็น Postgres function (transaction เดียว, all-or-nothing) API เป็นชั้นบาง
- **Business date** ต่อสาขา (ตัดวันเวลา 05:00 ได้) และล็อกงวดหลังปิดยอด
- เลขเอกสารไม่ข้ามเลข (gap-free) ต่อสาขา/ประเภท/งวด
- Domain events → outbox (`app.domain_events`) + `pg_notify` → SSE realtime
- ห้าม hard-code อัตรา GP/VAT/ค่าธรรมเนียม ทุกอย่างตั้งค่าได้และมีวันเริ่มมีผล

รายละเอียด: [04-architecture.md](04-architecture.md), [05-database.md](05-database.md), [06-api.md](06-api.md)

## กติกาด้าน UX/UI

- ปุ่มแตะ ≥ 44px ทุกที่, ปุ่มหลักใน POS/KDS ≥ 56px (WCAG 2.5.8 ขั้นต่ำ 24px)
- Contrast ≥ 4.5:1 ทุก token ทั้งโหมดสว่าง/มืด; จอครัวเป็น dark high-contrast
- สีสถานะมาพร้อมไอคอน + ข้อความเสมอ
- Motion: 150–300ms, spring สำหรับการแตะ, เคารพ `prefers-reduced-motion`
- กราฟ: แกนเดียว, เส้นบาง, tooltip ทุกกราฟ, มีมุมมองตาราง, palette ผ่านการตรวจ CVD
- ภาษาไทยเป็นหลัก ตัวเลขแบบ tabular, ปี พ.ศ. ในการแสดงผล (เก็บ ISO)

## Quality Gates (ต้องผ่านก่อน merge)

| Gate | เกณฑ์ | คำสั่ง |
|---|---|---|
| Typecheck | 0 error ทุก package | `pnpm typecheck` |
| Unit/Integration | ผ่านทั้งหมด (SQL e2e, domain, API, web) | `pnpm test` + `pnpm db:test` |
| Build | `next build` สำเร็จ | `pnpm build` |
| Accessibility | axe WCAG 2.2 AA = **0 violations** (สว่าง/มืด/dialog/มือถือ) | `tools/qa` → `npm run axe` |
| Lighthouse | Desktop 100 ทุกหมวด, Mobile Perf ≥ 90, A11y/BP/SEO = 100 | `tools/qa` → `npm run lighthouse` |

## Definition of Done

1. มีเทสต์ที่ล้มก่อนแก้และผ่านหลังแก้ (ถ้าเป็นบั๊ก)
2. สิทธิ์ถูกตรวจที่ **ฐานข้อมูล** ไม่ใช่แค่ UI
3. ข้อความ error ใหม่มีใน `ERROR_CATALOG` ทั้งไทย/อังกฤษ
4. หน้าใหม่: มี empty state, loading, error, มือถือ, dark mode, keyboard, ผ่าน axe
5. อัปเดตเอกสารที่เกี่ยวข้อง และ ADR ถ้าเป็นการตัดสินใจเชิงสถาปัตยกรรม
