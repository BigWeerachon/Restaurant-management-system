## วิธีทำงานต่อ (Resume protocol)

1. `git pull` branch `claude/restaurant-saas-master-prompt-s0yy8e` แล้วเปิดไฟล์นี้
2. เลือก **ข้อแรกที่ยังไม่ติ๊ก** ในเฟสที่เลขน้อยที่สุด (ข้าม 🔑 ที่ยังไม่มีข้อมูล — ทำส่วนที่ไม่ต้องใช้ข้อมูลนั้นไปก่อน)
3. ทำงาน → ตรวจตาม "เกณฑ์ผ่าน" ของเฟส → ติ๊กในไฟล์นี้ + เขียนหมายเหตุสั้นๆ ใน "บันทึกความคืบหน้า"
4. commit + push (CI ต้องเขียว) แล้วทำข้อถัดไป
5. ทุกเฟสจบ → อัปเดต docs/scorecard และสรุปให้เจ้าของโปรเจกต์

**เกณฑ์ผ่านทุกข้อ:** `pnpm typecheck` · `pnpm test` (รวม SQL e2e + API กับ Postgres จริง) · `pnpm build` ผ่าน;
หน้าเว็บที่แก้ต้องทำงานได้ **ทั้งโหมด demo และโหมด API** และ axe = 0 violations

## เฟส 3 — Data layer ฝั่งเว็บ

**บันทึกการสำรวจก่อนทำ 3.1** (ทำไว้ท้ายรอบก่อนหน้า จะได้ไม่ต้องสำรวจซ้ำ): เทียบ `apps/web/src/lib/demo/engine.ts` (ทุกฟังก์ชัน `export function ...(state, ctx, ...)` ที่แก้ state — มี 40 ฟังก์ชัน) กับ endpoint ที่มีตอนนี้ พบว่า **ทุกคำสั่งในเดโมมี endpoint คู่กันแล้วครบ** (เฟส 2 ที่เพิ่งทำจบคือของที่ 3.1–3.2 ต้องใช้พอดี) ยกเว้นจุดเล็กจุดเดียว: `updateChannel` ในเดโมรับ `priceMarkup` ได้ (ราคาที่ชาร์จเพิ่มตามช่องทางเดลิเวอรี) แต่ `app.sales_channels` ไม่มีคอลัมน์นี้เลย — เป็น gap เล็กๆ ที่ยังไม่ได้แก้ (backlog: เพิ่มคอลัมน์ `price_markup` + ผูกเข้า `app.resolve_menu_price` ทีหลัง ไม่ block 3.1)

สถาปัตยกรรมปัจจุบันของเว็บ (`apps/web/src/lib/demo/store.ts`): `useSabai` เป็น Zustand store เก็บ `db: DemoState` ทั้งก้อน หน้าเว็บเรียก `useSabai.getState().run((draft, ctx) => someEngineFn(draft, ctx, ...))` — `run()` ห่อด้วย Immer ทำ mutation แบบ atomic แล้ว `set({db: next})` ทีเดียว ทุกหน้า/component/selector (`selectors.ts`) อ่านจาก `db: DemoState` ก้อนเดียวกันเสมอ

**ทางเลือกที่ยืนยันจาก ADR-0009 และคุ้มที่สุด**: ให้ `HttpDataSource` คง**รูปร่าง `DemoState` เดิมทุกอย่าง** เป็น local mirror (ไม่ใช่ type ใหม่) — เพราะทุกหน้า/`selectors.ts` ผูกกับ `DemoState` อยู่แล้ว ถ้า mapper แปลงข้อมูลจาก API ให้ออกมาเป็น `DemoState` ได้ เฟส 4 (ย้ายหน้า) แทบไม่ต้องแตะ logic การอ่านข้อมูลเลย แก้แค่จุดที่เรียก `useSabai.getState().run(...)` ให้เรียกผ่าน `ds.xxx(...)` แทน วิธีนี้ทำให้ 3.1 ต้องออกแบบ:
1. `interface DataSource { loadShop(): Promise<DemoState>; commands: {...}; queries: {...} }` — `commands` มี 1 เมธอดต่อฟังก์ชันเดโมทั้ง 40 ตัว signature ใกล้เคียงเดิมแต่เป็น async และไม่รับ `state`/`ctx` ตรงๆ (adapter จัดการเอง)
2. `DemoDataSource` (3.2): เรียก `useSabai.getState().run(...)` ตรงๆ เหมือนเดิมทุกอย่าง (เทสต์เดิมต้องผ่านไม่มีการเปลี่ยนพฤติกรรม)

**สิ่งสำคัญที่พบตอนจะเริ่ม 3.2 (ต้องแก้ไปพร้อมกัน ไม่ใช่แค่ห่อ engine เฉยๆ):** หน้าเว็บไม่ได้เรียก `useSabai.getState().run(...)` ตรงๆ แต่ผ่าน `useAction()` (`apps/web/src/hooks/use-sabai.ts` บรรทัด ~111) ซึ่งให้ `{ exec, pending }` — `exec(command, opts)` รับ `command: (draft, ctx, approverId?) => T` (ยังผูกกับรูปแบบ engine ตรงๆ ไม่ใช่ `DataSource`) และมี behavior สำคัญที่ต้องคงไว้ให้เหมือนเดิมทั้งสองโหมด: ถ้า command throw `APPROVAL_REQUIRED` **และ** `opts.approval` ถูกส่งมา จะเปิด dialog ขอ PIN ผู้จัดการ (`useUi().requestApproval`) แล้ว **เรียก command เดิมซ้ำ** พร้อม `approverId` ที่ได้ ถ้าไม่ใช่ `APPROVAL_REQUIRED` หรือไม่ได้ตั้ง `opts.approval` จะ throw ต่อให้ `exec` แสดง toast error เอง (`showError`)

**แก้แผนแล้ว (สำคัญ): อย่าแก้ `useAction`/`exec` เดิมในที่เดิม** — มันจะบังคับให้ต้องแก้ทั้ง 13 หน้าพร้อมกันในตอนเดียว ขัดกับข้อดีของ ADR-0009 เองที่บอกว่า "ย้ายทีละหน้าได้" ทางที่ถูกคือทำคู่ขนาน:
(ก) เขียน `DemoDataSource` ให้ implement `DataSource` โดยแต่ละเมธอดเรียก `useSabai.getState().run((draft, ctx) => engineFn(draft, ctx, ..., approvalToken?.value))` ภายใน — ไฟล์/โค้ดเดิม (`useAction`, `ApprovalDialog`, ทุกหน้า) **ไม่ต้องแตะเลย** ยังทำงานเหมือนเดิม 100%
(ข) เพิ่ม hook **ใหม่** (เช่น `useDsAction()` ในไฟล์ใหม่ `apps/web/src/hooks/use-data-source.ts` คู่กับ `useDataSource()` ที่คืน instance ปัจจุบันจาก context/provider) รับ `command: (ds: DataSource, approval?: ApprovalToken) => Promise<T>` แทน `(draft, ctx, approverId?) => T` เดิม ข้างในจับ `APPROVAL_REQUIRED` เหมือนเดิมทุกอย่าง แต่เปลี่ยนจาก "เรียก command ซ้ำพร้อม approverId" เป็น "เรียก `ds.approve(permission, pin)` ได้ `ApprovalToken` แล้วเรียก command เดิมซ้ำพร้อม token" — หน้าที่ยังไม่ย้าย (เฟส 4) ใช้ `useAction` เดิมกับ engine ตรงๆ ต่อไปได้ปกติ ส่วน `ApprovalDialog` ก็ต้องมีคู่ใหม่ (หรือแตกเป็น presentational + 2 ตัวเรียก `ds.approve` ต่างกันตามโหมด) เพราะเวอร์ชันเดิมเรียก `approverByPin` ตรงจาก `db` แบบ sync — ทำให้ API mode ใช้ไม่ได้ (ต้อง await `ds.approve`)
ทั้งสอง path (เก่า `useAction`+engine ตรง, ใหม่ `useDsAction`+`DataSource`) ใช้ `useSabai` store เดียวกันอยู่ดี (เพราะ `DemoDataSource` ก็ยังเรียก `run()` เดิมข้างใน) จึง**ไม่มี state สองชุดขัดกัน** ระหว่างหน้าที่ย้ายแล้วกับยังไม่ย้าย — ปลอดภัยที่จะทำทีละหน้าจริงตามที่ ADR สัญญาไว้

**สิ่งที่ต้องแก้ใน `types.ts` (3.1) ก่อนเริ่มเขียน `DemoDataSource` จริง**: ตอนเขียน 3.1 เดาชนิดค่าคืนของบางคำสั่งจาก engine โดยไม่ได้ไล่โค้ดจริงทุกบรรทัด พบแล้วว่าอย่างน้อย `openShift` ของจริงคืน `id: string` (id ของกะที่เปิด) **ไม่ใช่** object `Shift` แบบที่ `types.ts` ประกาศไว้ (`Promise<Shift>`) วิธีที่ปลอดภัยที่สุดตอนเขียน `DemoDataSource`: **อย่าเดาจาก signature เดิม** ให้เขียนแต่ละเมธอดเรียก engine ตรงๆ ก่อน ปล่อยให้ `tsc` ฟ้อง type mismatch กับ `DataSource` แล้วค่อยแก้ชนิดใน `types.ts` ให้ตรงกับของจริงทีละจุด (เชื่อ compiler มากกว่าที่เดาไว้ในเอกสารนี้หรือใน docstring ของ `types.ts`) จุดที่มีแนวโน้มเดาผิดอีก (ยังไม่ตรวจ): `closeShift`, `receiveGoods`, `startCount`, `submitCount`, `approveCount`, `createPurchaseOrder`, `closeDay`, `addExpense` — ให้ตรวจให้ครบตอนเขียนจริง
3. `HttpDataSource` (3.3–3.4): แต่ละคำสั่งเรียก endpoint คู่กันจากเฟส 2 ที่เพิ่งทำ แล้ว **refetch slice ที่กระทบแทนการ patch เอง** (server เป็น source of truth อยู่แล้ว, ง่ายกว่าและถูกกว่าความเสี่ยงจาก patch ผิด) เช่น หลัง `submitOrder` → refetch orders+tickets+stock, หลัง `receiveGoods` → refetch stock+movements ต้องทำตารางแมป "คำสั่ง → slice ที่ต้อง refetch" ให้ครบใน 3.3
4. Approval (3.6): เดโม approverId = member id ตรงๆ, API ต้องเรียก `POST /v1/approvals` ก่อนได้ approvalId มาแนบกับคำสั่งจริง — ห่อเป็น `ds.requestApproval(permission, pin, target?)` คืนค่า token กลางๆ ที่ทั้งสอง adapter คืนคนละแบบแต่ shape เดียวกัน
