# SLO — ระบบต้องขายได้ ขายเร็ว และขายถูกต้อง (ข้อ 9.4)

หลักคิด: ผู้ใช้ของเราคือพนักงานหน้าร้านที่ลูกค้ายืนรออยู่ ความน่าเชื่อถือจึงวัดที่ **"ขายได้ไหม เร็วไหม ตัวเลขถูกไหม"** ไม่ใช่ที่ CPU ของเซิร์ฟเวอร์ SLO ด้านล่างเขียนบนตัวเลขที่ระบบวัดอยู่แล้ว (`docs/09-observability.md`) และตัวเลขฐานที่วัดจริง

## เป้าหมาย

| # | สิ่งที่ผู้ใช้รู้สึก | SLI (วัดอะไร) | เป้าหมาย | ช่วง | มาจาก |
|---|---|---|---|---|---|
| 1 | ขายได้ | สัดส่วนคำขอที่ **ไม่** ตอบ 5xx | ≥ **99.9%** (พลาดได้ < 0.1%) | 30 วัน | `http.server.request.duration` (นับตาม `http.response.status_class`) |
| 2 | ขายเร็ว | p95 เวลาตอบของ API ฝั่งเซิร์ฟเวอร์ | < **200 ms** | 5 นาทีต่อเนื่อง / 30 วัน | `http.server.request.duration` |
| 2b | | p99 | < 500 ms | เหมือนกัน | เหมือนกัน |
| 3 | การขายไม่ถูกหยุดด้วยค่าบริการ | จำนวน `BILLING_RESTRICTED` บน route ที่เป็นการขาย/รับเงิน/ปิดยอด/ครัว | **0** | ตลอดเวลา | `sabai.api.errors{code="BILLING_RESTRICTED"}` แยกตาม `route` |
| 4 | ตัวเลขถูกต้อง | บัญชีไม่สมดุล (`JOURNAL_UNBALANCED`), เลขใบเสร็จข้าม | **0** | ตลอดเวลา | `sabai.api.errors{code="JOURNAL_UNBALANCED"}`; ฐานข้อมูลบังคับไว้แล้วด้วย constraint (เทสต์ SQL) จึงเป็นสัญญาณเตือน ไม่ใช่เป้าหมายที่ต้องลุ้น |
| 5 | ครัวเห็นออเดอร์ทันที | ตั๋วครัวขึ้นจอภายใน 2 วินาทีหลังส่งจากหน้าขาย (p95) | < 2 s | 30 วัน | **ยังไม่วัด** — ต้องมี synthetic probe (ดูข้อจำกัด) |

**อะไรนับเป็นความผิดพลาด:** เฉพาะ 5xx (เซิร์ฟเวอร์พลาดเอง) — 4xx (`401/402/403/409/422/429`) คือผู้เรียกทำผิดหรือระบบปฏิเสธโดยตั้งใจ (PIN ผิด, แผนเต็ม, ค่าบริการค้าง) ไม่นับ **ไม่นับ:** `/health`, `/v1/events` (การเชื่อมต่อค้างยาว) และ `/v1/billing/webhook/*` `/v1/billing/run` (ผู้เรียกคือระบบอื่น)

## วัดอย่างไร

ชื่อ metric ตาม OpenTelemetry; เมื่อส่งผ่าน Prometheus จุดจะกลายเป็น `_` และหน่วยต่อท้าย (`http_server_request_duration_seconds_*`) — ตัวอย่างข้อความค้น (ปรับตามผู้ให้บริการ):

```promql
# 1) สัดส่วนที่สำเร็จ (ไม่ใช่ 5xx), 30 วัน
1 - (
  sum(increase(http_server_request_duration_seconds_count{http_response_status_class="5xx", http_route!~"/health|/v1/events|/v1/billing/.*"}[30d]))
  / sum(increase(http_server_request_duration_seconds_count{http_route!~"/health|/v1/events|/v1/billing/.*"}[30d]))
)

# 2) p95 ของ API ทั้งหมด (5 นาที) และของ route ขายโดยเฉพาะ
histogram_quantile(0.95, sum by (le) (rate(http_server_request_duration_seconds_bucket{http_route!~"/health|/v1/events"}[5m])))
histogram_quantile(0.95, sum by (le) (rate(http_server_request_duration_seconds_bucket{http_route=~"/v1/orders|/v1/orders/:id/pay"}[5m])))

# 3) ค่าบริการไม่ควรแตะเส้นทางการขาย — ต้องเป็น 0 เสมอ
sum(increase(sabai_api_errors_total{code="BILLING_RESTRICTED", route=~"/v1/orders.*|/v1/shifts.*|/v1/kds.*|/v1/days.*"}[1h]))
```

`BILLING_RESTRICTED` ควรเกิดได้เฉพาะ `POST /v1/branches`, `POST /v1/members`, `POST /v1/devices` (เพิ่มสาขา พนักงาน เครื่อง) — ถ้าเห็นบน route อื่น คือบั๊กที่ทำให้ค่าบริการหยุดการขาย ซึ่งเป็นกฎที่ห้ามผิด (มีเทสต์ SQL/API/เบราว์เซอร์คุมอยู่แล้ว)

## งบข้อผิดพลาดและการแจ้งเตือน

99.9% ใน 30 วัน = พลาดได้ราว **43 นาที** (หรือ 0.1% ของคำขอ) แจ้งเตือนตาม **อัตราการเผางบ** (burn rate) ไม่ใช่ตามค่าดิบ:

| ระดับ | เงื่อนไข | ทำอะไร |
|---|---|---|
| เรียกคนทันที | เผางบ 14.4 เท่า (ใช้ 2% ของงบใน 1 ชม.) ทั้งหน้าต่าง 1 ชม. **และ** 5 นาที | ตรวจทันที — ร้านกำลังขายไม่ได้ |
| แจ้งในเวลางาน | เผา 6 เท่าทั้ง 6 ชม. และ 30 นาที | ตรวจภายในวัน |
| ตั๋ว | เผา 1 เท่าทั้ง 3 วัน | จัดเข้าคิวงาน |
| เรียกคนทันที (ไม่ใช้งบ) | `sabai.api.errors{code="JOURNAL_UNBALANCED"}` > 0 หรือ `BILLING_RESTRICTED` บน route การขาย > 0 | หยุดดูทันที — ข้อมูลหรือกฎหลักผิด |

**เมื่องบหมด:** หยุดปล่อยฟีเจอร์ใหม่จนกว่าจะแก้ต้นเหตุ (เปิดได้เฉพาะแก้ความน่าเชื่อถือ/ความปลอดภัย) และทบทวนเหตุการณ์ (blameless) ก่อนกลับไปปล่อยตามปกติ

## ตัวเลขฐานที่วัดจริง

วัดด้วย `tools/load/probe.mjs` (ขาย+รับเงิน 1 ใน 4 คำขอ ที่เหลืออ่านจอครัว/บิลของวัน/สรุปวันนี้/สต็อก) บนเครื่องพัฒนา **4 vCPU** โดย API (Node 22, โปรเซสเดียว) ฐานข้อมูล Postgres 16 และตัวยิงโหลดอยู่เครื่องเดียวกัน — จึงวัดทั้งโค้ดและเครื่อง ใช้เทียบแบบเดียวกันกับแบบเดียวกันเท่านั้น (**ไม่ใช่** ตัวเลขของ production)

| ที่ 4 คำขอพร้อมกัน (~85 คำขอ/วินาที, 20 วินาที) | p50 | p95 | p99 |
|---|---:|---:|---:|
| `GET /v1/kds/tickets` | 31 | 88 | 129 |
| `GET /v1/orders?detail=full` (บิลทั้งวัน ราว 700 ใบ) | 99 | 164 | 187 |
| `GET /v1/reports/today` | 45 | 112 | 135 |
| `GET /v1/stock` | 19 | 84 | 117 |
| `POST /v1/orders` | 25 | 80 | 102 |
| `POST /v1/orders/:id/pay` | 22 | 72 | 101 |

ข้อผิดพลาดของเซิร์ฟเวอร์: **0** (0.000%) จาก 1,696 คำขอ — ผ่านทั้งสองเป้า (p95 < 200 ms, พลาด < 0.1%)

ที่ 8 คำขอพร้อมกัน throughput ยังราว 80/วินาที (ไม่เพิ่ม) แต่ p95 ขึ้นเป็น 148–279 ms — **เป็นการต่อคิวของโปรเซสเดียว ไม่ใช่โค้ดช้าลง** (`reports/today` ตอบ 13–16 ms เมื่อยิงทีละคำขอ) สรุปคือ 1 instance บนเครื่องระดับนี้รับได้ราว 4 คำขอพร้อมกัน / ~85 ต่อวินาที ก่อนจะเกิน 200 ms ที่ p95 เกินกว่านั้นต้องเพิ่ม instance (API ไม่เก็บสถานะของร้านไว้ในโปรเซส; ที่อยู่ในหน่วยความจำต่อ instance มีแค่ตัวจำกัดอัตรา PIN, ตัวลดรายงานข้อผิดพลาดซ้ำ และตัวกระจายเหตุการณ์สด (ซึ่งฟัง `NOTIFY` ของฐานข้อมูลเอง จึงใช้หลาย instance ได้) — ยังไม่ได้ทดลองรันหลาย instance)

**ผลข้างเคียงที่ดีที่สุดของการวัดครั้งแรก:** `GET /v1/orders` ช้า 204 ms (p50) กับบิล 350 ใบ ทั้งที่คิวรีในฐานข้อมูลใช้ 1.3 ms — สาเหตุคือเรียก `app.business_date(สาขา)` ใน `WHERE` ตรง ๆ ทำให้ Postgres รันฟังก์ชันนั้น *ทุกแถว* (ครึ่งมิลลิวินาที × 350) เพราะเป็นฟังก์ชัน `stable` ของพารามิเตอร์ที่ bind ไว้ ซึ่ง planner ไม่ยุบเป็นค่าเดียว แก้ด้วย `(select app.business_date(…))` (คำนวณครั้งเดียว): **204 → 12 ms** (รายการเปล่า) และ **269 → 55 ms** (`detail=full` ที่ 350 ใบ) (ที่ตารางเล็ก planner เลือก seq scan ซึ่งรันฟังก์ชันทุกแถว; ที่ตารางใหญ่น่าจะใช้ index แล้วคำนวณครั้งเดียว แต่ยังไม่ได้วัด — คิวรีที่แก้แล้วถูกต้องทั้งสองกรณี)

## ข้อจำกัดที่รู้อยู่

- **ตัวเลขฐานมาจากเครื่องพัฒนา ไม่ใช่ production** และไม่มีการทดสอบโหลดต่อเนื่องนานหลายชั่วโมง ยังไม่รู้พฤติกรรมเมื่อ DB ใหญ่ (หลายเดือนของบิล) หรือมีหลายร้านพร้อมกัน — ต้องวัดซ้ำบนโครงสร้างจริงก่อนเปิดให้ลูกค้าจริง
- **`GET /v1/orders?detail=full` ส่งบิลทั้งวันทุกครั้ง** (445 KB ที่ ~350 ใบ, จำกัดที่ 500) และหน้าจอโหลดซ้ำเมื่อมีเหตุการณ์ `order.*` — ร้านที่ขายวันละหลายร้อยใบจะเสียเวลาส่วนใหญ่ที่ JSON มากกว่าฐานข้อมูล ทางแก้ที่ควรทำต่อ: ดึงเฉพาะบิลที่เปลี่ยนตั้งแต่เวลาล่าสุด (`since`) แทนทั้งวัน
- **SLO ข้อ 5 (ครัวเห็นภายใน 2 วินาที) ยังไม่วัด** เพราะต้องมีตัวตรวจสังเคราะห์ที่ส่งออเดอร์แล้วดูจอครัว (หรือ metric ฝั่งเบราว์เซอร์ที่ยังไม่มี — `docs/09-observability.md`) และ offline (ขายตอนเน็ตหลุดแล้วส่งเมื่อกลับมา) ยังไม่มี SLO เพราะยังไม่มีตัวเลขจากเครื่องจริงของร้าน
- **ยังไม่มี dashboard/alert จริง** (ไม่มี collector ที่ deploy) — เอกสารนี้คือข้อกำหนดที่ต้องตั้งเมื่อมี; ข้อความค้นข้างบนเขียนตามชื่อ metric จริงแต่ยังไม่ได้ทดสอบกับ Prometheus/Grafana จริง
- `probe.mjs` ไม่ได้อยู่ใน CI โดยตั้งใจ (ตัวเลขบน runner ที่ใช้ร่วมกันแกว่งเกินกว่าจะใช้เป็นประตู) ใช้เป็นเครื่องมือก่อนปล่อย/หลังเปลี่ยนคิวรี: `node tools/load/probe.mjs` (ออกด้วยรหัส 1 ถ้า p95 > 200 ms หรือพลาด > 0.1%)

## รันตัววัด

```bash
pnpm db:reset && pnpm db:seed && pnpm --filter @sabai/api dev   # API ที่มีข้อมูลตัวอย่างบน :8787
node tools/load/probe.mjs                                        # 20 วินาที ทีละ 4 คำขอ
DURATION_S=60 CONCURRENCY=8 node tools/load/probe.mjs            # ยาวขึ้น/หนักขึ้น
```
