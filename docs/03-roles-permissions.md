# บทบาทและสิทธิ์ (Roles & Permissions)

> หลักการ: **"พนักงานไม่จำเป็นต้องเข้าใจระบบ แต่ระบบต้องเข้าใจวิธีทำงานของพนักงาน"**
> แต่ละคนเห็นเฉพาะงานของตัวเอง เมนูหลักไม่เกิน 5 รายการ (Hick's law) ที่เหลืออยู่ใต้ "เพิ่มเติม"

ตารางทั้งหมดในหน้านี้ **สร้างจากโค้ด** (`packages/domain/src/permissions.ts`) — ฐานข้อมูล seed ชุดเดียวกัน
และมี API test (`keeps the permission catalog in code and database in sync`) ที่ล้มทันทีถ้าสองฝั่งไม่ตรงกัน

## 1. โมเดลสิทธิ์

| แนวคิด | รายละเอียด |
|---|---|
| **Permission** | 34 สิทธิ์ แบ่งตามโมดูล มีระดับความเสี่ยง (ต่ำ/กลาง/สูง) ใช้แสดงป้าย "สำคัญ" ในหน้าตั้งค่าสิทธิ์ |
| **Role** | ชุดสิทธิ์ + หน้าแรก (home) + สี; ร้านสร้างตำแหน่งเองได้ (custom role) |
| **Owner** | `grants_all = true` — ได้สิทธิ์ทุกอย่าง **รวมถึงสิทธิ์ที่จะเพิ่มในอนาคต** จึงไม่ต้องตั้งค่าใหม่เมื่ออัปเกรด |
| **Membership** | คน × ร้าน × ตำแหน่ง × สาขา (ทุกสาขา หรือบางสาขา) + วงเงินส่วนตัว เช่น ลดราคาได้เองไม่เกิน 10% |
| **PIN-only staff** | พนักงานพาร์ทไทม์ไม่ต้องมีอีเมล ใช้ PIN 4–6 หลักบนเครื่องร้าน (JWT มี claim `mid`) |
| **Manager approval** | การกระทำเสี่ยง (ยกเลิกรายการที่ส่งครัวแล้ว, คืนเงิน, ส่วนลดเกินวงเงิน) → ผู้มีสิทธิ์ใส่ PIN อนุมัติ ใช้ได้ **ครั้งเดียวภายใน 5 นาที** และบันทึกทั้งผู้ขอและผู้อนุมัติใน audit log |
| **Last owner guard** | ลด/ปิดเจ้าของร้านคนสุดท้ายไม่ได้ (trigger `app.protect_last_owner` + engine) กันร้านถูกล็อก |

### ชั้นการบังคับใช้ (defense in depth)

1. **ฐานข้อมูล** — RLS ทุกตาราง + ทุกคำสั่งเขียน (`security definer` function) เรียก `app.assert_permission()` ก่อนทำงาน
   *แม้ API มีบั๊ก ข้อมูลร้านอื่นก็ไม่รั่ว*
2. **API** — `route({ permission })` ตรวจก่อนเข้า handler และทุก request รันใน `set local role authenticated` พร้อม JWT claims
3. **UI** — เมนูสร้างจากสิทธิ์ (`navigationFor`), deep link ตรวจด้วย `routeAllowed` → แสดงหน้าอธิบายแทนหน้าว่าง
   (UI เป็นแค่ความสะดวก ไม่ใช่ความปลอดภัย)

## 3. การอนุมัติด้วย PIN (ตัวอย่างสถานการณ์)

| สถานการณ์ | ใครทำได้เอง | ถ้าไม่มีสิทธิ์ |
|---|---|---|
| ลดราคา ≤ วงเงินส่วนตัว (เช่น แคชเชียร์ 10%) | ผู้มี `pos.discount` | — |
| ลดราคาเกินวงเงิน | ผู้มีวงเงินสูงกว่า | ขอ PIN ผู้จัดการ (`DISCOUNT_OVER_LIMIT`) |
| ลบรายการที่ **ยังไม่ส่งครัว** | ทุกคนที่รับออเดอร์ได้ | — |
| ยกเลิกรายการที่ **ครัวรับแล้ว** | ผู้มี `pos.void` | ขอ PIN (`APPROVAL_REQUIRED`) |
| คืนเงินทั้งบิล | ผู้มี `pos.refund` | ขอ PIN |
| ปรับยอดสต็อกหลังนับ | ผู้มี `inventory.adjust` | ผลนับรออนุมัติ |

ทุกการอนุมัติบันทึกใน `app.approvals` (ใช้ครั้งเดียว) และ `audit.log` — เจ้าของร้านดูย้อนหลังได้ในฟีด "ความเคลื่อนไหวล่าสุด"
